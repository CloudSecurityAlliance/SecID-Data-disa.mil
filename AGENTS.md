# AGENTS.md

This file provides vendor-neutral guidance to AI coding agents when working with code and data in this repository. `CLAUDE.md` (`@AGENTS.md`) and `GEMINI.md` (`@./AGENTS.md`) point here so all agents read the same canonical instructions.

## Repository Overview

Structured DISA STIG and SRG content for [SecID](https://github.com/CloudSecurityAlliance/SecID).

DISA publishes STIGs as XCCDF XML inside per-document ZIPs inside a quarterly compilation. There is **no per-rule permalink upstream** — you cannot link to `V-257505` anywhere on `cyber.mil`. This repository exists so that a SecID for a rule resolves to structured, provenance-tracked JSON.

## Layout & Path Derivation

Standard for every `SecID-Data-*` repository, mirroring the registry's reverse-DNS convention so one path-derivation algorithm works everywhere:

```
data/         extracted content, addressed by SecID
schemas/      JSON Schema for the record formats
scripts/      acquisition, extraction and validation tooling
indexes/      generated by scripts — never hand-edited
docs/         how it works, source quirks, provenance
```

| Script | Does |
|---|---|
| `scripts/fetch_compilation.py` | Downloads a quarterly compilation and records its whole-archive SHA-256 in `indexes/compilations.json` |
| `scripts/extract_stigs.py` | Extracts one compilation into `data/` and rewrites `indexes/corpus.json` |
| `scripts/validate.py` | Checks every record against `schemas/` and the layout rules; run by CI on every push and PR |

A SecID maps to a path mechanically:

```
secid:control/disa.mil/rhel-9@V2R9#V-257505
   -> data/control/mil/disa/rhel-9/V2R9/rules/V-257505.json
      ────  ───────  ────────  ──────  ────       ──────────
      data    type    domain    name  release      subpath
                  (reverse-DNS)
```

STIGs and SRGs both live under `control/` because that is the SecID type both resolve as. `kind` distinguishes them as a field, not as a directory — structure follows the identifier, never the publisher's filing cabinet.

## Identifiers

Each rule carries four, and they are not interchangeable:

| Field | Example | Notes |
|---|---|---|
| `vuln_id` | `V-257505` | Stable across revisions. This is the subpath. |
| `rule_id` | `SV-257505r960759_rule` | Carries a revision counter; changes when the rule changes. |
| `stig_id` | `CNTR-OS-000010` | Human-facing, per-benchmark prefix. |
| `idents.cci` | `CCI-000068` | Maps to NIST SP 800-53. A rule may carry several. |

`idents.legacy` holds superseded V/SV numbers where DISA recorded them, so historical citations still resolve.

Severity maps to the familiar categories: `high` = CAT I, `medium` = CAT II, `low` = CAT III.

## Versions & Retention

Both DISA schemes are present, and DISA is mid-migration between them:

- `V<major>R<minor>` — e.g. `V2R9`
- `Y<yy>M<mm>` — e.g. `Y26M07`

Releases are **retained, not replaced**. Latest-1 matters in practice: SCAP Compliance Checker ships SCAP content one release behind the manual STIG, so scan results in the field routinely reference the older release.

## Provenance

Every `stig.json` records the source compilation, the inner archive name, and that inner archive's SHA-256. `indexes/compilations.json` records the SHA-256, size and `Last-Modified` of each **whole** compilation, so a record traces back to an exact upstream artifact. Each quarterly ingest is a single commit, tagged `vYYYY.MM`.

```bash
git diff v2026.04 v2026.07 -- data/         # what DISA changed last quarter
git log -- data/control/mil/disa/rhel-9/    # every release of one STIG
```

`provenance.source_compilation` names the **most recent** compilation that contained the release, not the first. A release that appears unchanged in several compilations is rewritten at each ingest, and this field moves forward. To find the compilation a release first appeared in, use `git log --diff-filter=A` on its `stig.json`.

## Indexes (Generated Only)

Both files under `indexes/` are generated by scripts. **Do not edit them by hand.**

- **`indexes/corpus.json`** lists the **latest ingested compilation only**: its name, document and rule counts, and one entry per document release in it. `extract_stigs.py` rewrites it on every run, so it is not a catalogue of the repository. Older releases are still present under `data/`; to list them, walk `data/control/mil/disa/*/*/stig.json`. The file for any earlier quarter is available at that quarter's tag (`git show v2026.04:indexes/corpus.json`).
- **`indexes/compilations.json`** keeps growing, with one entry per compilation ever fetched, and `fetch_compilation.py` refuses to overwrite an entry with a different hash.

## Quarterly Refresh & Cross-Repo Ordering

DISA publishes in January, April, July and October. A refresh touches two repositories, and **the order matters**. The registry's rule URLs point at this repository's `main` branch, so if the registry sync lands first, every new rule link 404s until the data arrives.

1. **Fetch** the compilation and record its hash:
   ```bash
   python3 scripts/fetch_compilation.py --dest ~/stig-archive      # newest published
   ```
2. **Extract** into `data/`, then **validate**:
   ```bash
   python3 scripts/extract_stigs.py ~/stig-archive/U_SRG-STIG_Library_October_2026.zip
   pip install jsonschema && python3 scripts/validate.py
   git diff --stat                         # expect new release dirs plus stig.json provenance bumps
   ```
   The extractor's output is byte-identical for unchanged content. If every rule file shows as modified, the serialisation has drifted: stop and fix the extractor, not the data.
3. **Land the data on `main`** in this repository: branch, a single commit `Ingest SRG/STIG Library Compilation <Month> <Year>`, PR, CI green, merge. Then tag the merge commit and push the tag:
   ```bash
   git tag vYYYY.MM <merge-commit> && git push origin vYYYY.MM
   ```
4. **Only then, sync the registry** in [SecID](https://github.com/CloudSecurityAlliance/SecID) with this repository checked out at the merged `main`:
   ```bash
   python3 scripts/sync-disa-stigs.py --dry-run --data-repo /path/to/SecID-Data-disa.mil
   python3 scripts/sync-disa-stigs.py --data-repo /path/to/SecID-Data-disa.mil
   ```
   If `--data-repo` points at a missing or stale checkout, `sync-disa-stigs.py` quietly writes document nodes with **no rule children**, so always check the dry-run output and the diff. The default `--data-repo` is `~/GitHub/CloudSecurityAlliance/SecID-Data-disa.mil`.

## Validation & Commit Conventions

- Run `python3 scripts/validate.py` before opening any PR touching `data/`, `schemas/`, `indexes/`, or `scripts/`.
- Never commit `*.zip` compilation archives to git (they are gitignored; ~370 MB each). Retain the original archive externally so it can be verified against `indexes/compilations.json`.
- Never push directly to `main`; use a feature branch and open a PR.
