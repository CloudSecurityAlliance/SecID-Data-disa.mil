# SecID-Data-disa.mil

Structured DISA STIG and SRG content for [SecID](https://github.com/CloudSecurityAlliance/SecID).

DISA publishes STIGs as XCCDF XML inside per-document ZIPs inside a quarterly compilation.
There is **no per-rule permalink upstream** — you cannot link to `V-257505` anywhere on
cyber.mil. This repository exists so that a SecID for a rule resolves to something.

## Layout

Standard for every `SecID-Data-*` repository, mirroring the registry's reverse-DNS convention
so one path-derivation algorithm works everywhere:

```
data/         extracted content, addressed by SecID
schemas/      JSON Schema for the record formats
scripts/      acquisition, extraction and validation tooling
indexes/      generated by scripts — never hand-edited
docs/         how it works, source quirks, provenance
```

| Script | Does |
|---|---|
| `scripts/fetch_compilation.py` | Downloads a quarterly compilation and records its whole-archive SHA-256 in `indexes/compilations.json` |
| `scripts/extract_stigs.py` | Extracts one compilation into `data/` and rewrites `indexes/corpus.json` |
| `scripts/validate.py` | Checks every record against `schemas/` and the layout rules; run by CI on every push and PR |

A SecID maps to a path mechanically:

```
secid:control/disa.mil/rhel-9@V2R9#V-257505
   -> data/control/mil/disa/rhel-9/V2R9/rules/V-257505.json
      ────  ───────  ────────  ──────  ────       ──────────
      data    type    domain    name  release      subpath
                  (reverse-DNS)
```

STIGs and SRGs both live under `control/` because that is the SecID type both resolve as.
`kind` distinguishes them as a field, not as a directory — structure follows the identifier,
never the publisher's filing cabinet.

## Identifiers

Each rule carries four, and they are not interchangeable:

| Field | Example | Notes |
|---|---|---|
| `vuln_id` | `V-257505` | Stable across revisions. This is the subpath. |
| `rule_id` | `SV-257505r960759_rule` | Carries a revision counter; changes when the rule changes. |
| `stig_id` | `CNTR-OS-000010` | Human-facing, per-benchmark prefix. |
| `idents.cci` | `CCI-000068` | Maps to NIST SP 800-53. A rule may carry several. |

`idents.legacy` holds superseded V/SV numbers where DISA recorded them, so historical
citations still resolve.

Severity maps to the familiar categories: `high` = CAT I, `medium` = CAT II, `low` = CAT III.

## Versions

Both DISA schemes are present, and DISA is mid-migration between them:

- `V<major>R<minor>` — e.g. `V2R9`
- `Y<yy>M<mm>` — e.g. `Y26M07`

Releases are **retained, not replaced**. Latest-1 matters in practice: SCAP Compliance
Checker ships SCAP content one release behind the manual STIG, so scan results in the field
routinely reference the older release.

## Provenance

Every `stig.json` records the source compilation, the inner archive name, and that inner
archive's SHA-256. `indexes/compilations.json` records the SHA-256, size and `Last-Modified`
of each **whole** compilation, so a record traces back to an exact upstream artifact.
Each quarterly ingest is a single commit, tagged `vYYYY.MM`.

```
git diff v2026.04 v2026.07 -- data/    # what DISA changed last quarter
git log -- data/control/mil/disa/rhel-9/   # every release of one STIG
```

`provenance.source_compilation` names the **most recent** compilation that contained the
release, not the first. A release that appears unchanged in several compilations is rewritten
at each ingest, and this field moves forward. To find the compilation a release first appeared
in, use `git log --diff-filter=A` on its `stig.json`.

The six ledger entries for April 2025 through July 2026 were hashed on 2026-09-24 from the
copies DISA was then serving. The four from April 2025 to January 2026 had been re-uploaded
on 2026-04-28 (their `Last-Modified`), after they were ingested. So all six were checked
before being recorded: every inner archive's SHA-256 matches the `inner_sha256` in the
`stig.json` at the corresponding tag.

## Indexes

Both files are generated. Do not edit them by hand.

- **`indexes/corpus.json`** lists the **latest ingested compilation only**: its name, document
  and rule counts, and one entry per document release in it. `extract_stigs.py` rewrites it
  on every run, so it is not a catalogue of the repository. Older releases are still present
  under `data/`; to list them, walk `data/control/mil/disa/*/*/stig.json`. The file for any
  earlier quarter is available at that quarter's tag (`git show v2026.04:indexes/corpus.json`).
- **`indexes/compilations.json`** keeps growing, with one entry per compilation ever fetched,
  and `fetch_compilation.py` refuses to overwrite an entry with a different hash.

## Refreshing (quarterly)

DISA publishes in January, April, July and October. A refresh touches two repositories, and
**the order matters**. The registry's rule URLs point at this repository's `main` branch, so if
the registry sync lands first, every new rule link 404s until the data arrives.

1. **Fetch** the compilation and record its hash:

   ```
   python3 scripts/fetch_compilation.py --dest ~/stig-archive      # newest published
   ```

2. **Extract** into `data/`, then **validate**:

   ```
   python3 scripts/extract_stigs.py ~/stig-archive/U_SRG-STIG_Library_October_2026.zip
   pip install jsonschema && python3 scripts/validate.py
   git diff --stat                         # expect new release dirs plus stig.json provenance bumps
   ```

   The extractor's output is byte-identical for unchanged content. If every rule file shows as
   modified, the serialisation has drifted: stop and fix the extractor, not the data.

3. **Land the data on `main`** in this repository: branch, a single commit
   `Ingest SRG/STIG Library Compilation October 2026`, PR, CI green, merge. Then tag the merge
   commit and push the tag:

   ```
   git tag v2026.10 <merge-commit> && git push origin v2026.10
   ```

4. **Only then, sync the registry** in [SecID](https://github.com/CloudSecurityAlliance/SecID)
   with this repository checked out at the merged `main`:

   ```
   python3 scripts/sync-disa-stigs.py --dry-run --data-repo /path/to/SecID-Data-disa.mil
   python3 scripts/sync-disa-stigs.py --data-repo /path/to/SecID-Data-disa.mil
   ```

   `sync-disa-stigs.py` reads the compilation manifest with two HTTP range requests (about
   150 KB, not the 370 MB archive). It refuses to write on a slug collision or a slug that is
   not a clean `[a-z0-9-]+` literal ([SecID #181](https://github.com/CloudSecurityAlliance/SecID/issues/181)).
   It enumerates V-IDs from `rule_index` in this repository. If `--data-repo` points at a
   missing or stale checkout, it quietly writes document nodes with **no rule children**, so
   check the dry-run output and the diff. The default `--data-repo` is
   `~/GitHub/CloudSecurityAlliance/SecID-Data-disa.mil`.

   Open the registry PR. Merging it deploys to the live resolver automatically.

## Archiving originals

DISA serves roughly the last six quarterly compilations. Older ones return 404, and because
per-STIG URLs also 404 once superseded, a dropped compilation **cannot be reconstructed from
anywhere upstream**. The zips are deliberately not in git (`*.zip` is ignored; ~370 MB each,
mostly PDFs).

Recommendation, not yet implemented: copy every fetched compilation to durable object storage
(R2, per the SecID roadmap's "originals and extraction artifacts in R2") keyed by file name,
and verify it against `indexes/compilations.json`. Until then, whoever runs the ingest should
keep the original zip. As of 2026-09-24 all six ingested compilations (April 2025 through July
2026) were still downloadable. April 2025 is the next expected to disappear.

## Not included

- **SCAP benchmarks** — absent from the compilation; only ~11 exist and they lag the manual STIG.
- **GPOs and SRR tools** — excluded by DISA from the compilation. Classification is an open
  question; see [SecID issue #186](https://github.com/CloudSecurityAlliance/SecID/issues/186).
- **PDFs** — overview, revision history and release memos are ~80% of the payload and carry no
  referenceable content. Originals belong in object storage, not git.
